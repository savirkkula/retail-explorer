# Data and semantic model

## Synthetic dataset

Generated by `data-gen/generate.py` with a fixed seed (`20261018`), so output is reproducible.

- Window: 2024-01-01 to 2026-09-30 (daily grain for sales, monthly for rent and energy).
- Portfolio 2025 totals are calibrated to the public figures: EUR 617.3M sales and 36.2M visitors.
- Areas: Forum 40,000 m2 and Ratina 52,000 m2 follow public sources. Citycenter retail (36,000 m2, 3 retail floors under 5 office floors) is an assumption. Per-center splits of sales and visitors are invented.
- Tenants: fictional brand names by category, plus three real brands (XXL, Elixia in Citycenter; Beyond Retro in Forum) with synthetic figures. `Tenant[Is Real Brand]` marks them.
- Floor plans are schematic and not to scale. `geometry.py` has three layouts: a ring around an atrium (Forum), a spine with end caps (Citycenter) and two wings joined by a bridge (Ratina). Office levels (Citycenter) and parking levels (Ratina) exist only as ghost slabs.

### Behaviour baked into the simulation

Seasonality (December peak, summer dip), weekday pattern, closed days (New Year, Independence Day, Christmas, Easter Sunday), category trends (food and beauty up, fashion and home down), per-center growth, hub and floor effects on sales, large-unit density discount, turnover rent as a top-up on base rent, and lease churn with vacancy gaps.

### Planted demo stories

| Story | Where | How to see it |
|---|---|---|
| Stressed stores | Forum level 3, six stores whose sales fall from April 2025 | Occupancy cost lens, red units above 15% |
| Lease expiry cliff | Forum level 2, eight leases ending Nov 2026 - Aug 2027 | Lease runway lens |
| Vacancy pocket | Ratina level 3, four units empty since January 2026 | Flat vacant units, "Vacant unit" store profile |
| Anchor effect | Citycenter level 1, XXL opens 2025-11-01 and lifts neighbouring sales and footfall | Sales growth lens |
| Energy outlier | Forum level 4 energy +30% from 2026 | Stored in `Energy`; no UI lens yet |

The XXL opening date is invented for the demo.

## Semantic model `sm_retail_explorer`

Generated from the parquet schema by `build_model.py`. Table and column names are display names derived from the Delta columns (`unit_key` becomes `Unit Key`); two columns are renamed to avoid clashing with measures (`Transaction Count`, `Visitor Count`).

### Relationships (many to one)

`Floor -> Property`, `Zone -> Floor`, `Unit -> Floor`, `Floor Shape -> Floor`, `Lease -> Unit`, `Lease -> Tenant`, `Sales -> Date / Unit / Tenant`, `Footfall -> Date / Zone`, `Rent -> Date (month) / Unit`, `Energy -> Date (month) / Floor`.

`Unit` has no relationship to `Zone` (that would create a second path to `Floor`). Zone footfall for a unit is computed with `TREATAS` instead.

### Measures

| Measure | Definition |
|---|---|
| Sales, Transactions | Sums of `Sales[Sales EUR]` and `Sales[Transaction Count]` |
| Sales PY, Sales YoY % | `DATEADD(..., -1, YEAR)` over the filtered period |
| Sales per m2 | Sales / occupied m2-months x 12 (annualised) |
| Base Rent, Turnover Rent, Total Rent, Service Charge, Occupancy Cost | Sums from `Rent` |
| OCR | (Total Rent + Service Charge) / Sales |
| Occupied Area, Leasable Area, GLA m2, Vacant Area m2, Occupancy % | Area measures in m2-months or averaged over the period |
| ERV per m2, Base Rent per m2, Rent vs ERV % | Market rent comparison on occupied area |
| Vacancy Rent Potential | ERV of vacant units over the period |
| Visitors, Visitors PY, Visitors YoY % | Footfall sums and year-on-year |
| Zone Visitors | Visitors in the unit's zone (`TREATAS`) |
| Sales per Passing Visitor | Sales / Zone Visitors |
| Lease Years Remaining, Lease Expiry Date, Active Tenant, Is Vacant | State of the active lease at the end of the filtered period |
| WAULT | Rent-weighted years to expiry of active leases |
| Expiring 12m Area m2 | Area of leases ending within 12 months of the period end |
| Category Benchmark Density | Sales per m2 of the unit's category within its center (unit level only) |
| Sales Index vs Category | Unit density / benchmark |
| Health Score | 0-100: 40% sales index, 30% OCR (8% = 100, 20% = 0), 15% YoY trend, 15% lease runway (5 years = 100) |
| Months in Period, Energy kWh, Energy Intensity | Helpers and energy |

Period handling: the app filters `'Date'[Date]` to a month-aligned range, and "end of period" measures use `MAX('Date'[Date])`.

## Rebuild and redeploy

Prerequisites: Python 3.12 with `numpy`, `pandas`, `pyarrow` (and `matplotlib` only for previews); an `az login` session in tenant `3ce6b0b4-da74-41c3-8955-a44959b72ad7`.

```bash
cd data-gen

# 1. Regenerate data (writes data-gen/out/*.parquet)
python3 generate.py

# 2. Upload data-gen/out/*.parquet to the Lakehouse Files/retail_explorer/ folder, then run
#    Load Table (Overwrite, Parquet) for each of the 12 tables.

# 3. Rebuild the TMDL and creation payload
python3 build_model.py <workspaceId> <lakehouseId> <sqlEndpointConnectionString>

# 4. Push the model and refresh (use --recreate when relationships changed)
python3 deploy_model.py <workspaceId> <modelId> [--recreate]
```

Notes:

- The model uses `Sql.Database` against the Lakehouse SQL analytics endpoint (Direct Lake on SQL endpoint). A Direct Lake on OneLake expression (`AzureStorage.DataLake`) failed refresh in this workspace.
- After new Delta tables are loaded the SQL endpoint may need a metadata refresh before the first model refresh succeeds.
- `updateDefinition` fails with `ThrowObjectNotFoundError` when relationships are removed. Delete and recreate instead (`--recreate`); the model id then changes, so update `fabric.yaml` with `npx fabric-app-data remove retailExplorer` and `npx fabric-app-data add semanticModel retailExplorer -w <ws> -i <newId>`, then `npx fabric-app-data generate -o src/fabric.generated.ts`.
- DAX reserved word: always quote `'Property'[...]`.

## App-owned tables (actions)

User-created data is not part of the Lakehouse or the semantic model. It lives in the SQL database that Rayfin provisions for the app item (`services.data`, dialect `mssql` in `rayfin/rayfin.yml`). The entities are TypeScript classes in `rayfin/data/`, registered in `rayfin/data/schema.ts`.

**`StoreAction`**

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | Primary key, generated by the server |
| `unitKey`, `propertyKey` | int | Match `Unit Key` and `Property Key` in the semantic model |
| `unitCode`, `storeName` | text | Denormalised for display (`storeName` is `Vacant` for empty units) |
| `actionType` | set | `renewal`, `rent-review`, `market-vacant`, `performance-review` |
| `status` | set | `open`, `in-progress`, `done`, `declined` |
| `priority` | set | `low`, `medium`, `high` |
| `title`, `triggerText` | text | `triggerText` keeps the flag text that raised the action |
| `dueDate`, `assignee` | optional | Assignee is an email address |
| `authorId`, `authorEmail` | text | From the signed-in session |
| `createdAt`, `updatedAt` | date | |

**`ActionComment`**: `id`, `action_id` plus a `@one` link to `StoreAction`, `body` (up to 1000 characters), `authorId`, `authorEmail`, `createdAt`.

Rayfin rules that shaped these: every text field has an explicit `max` (an unbounded `@text()` becomes `NVARCHAR(MAX)` and can break the GraphQL schema), every entity has an explicit permission decorator, and foreign keys follow the `{property}_id` naming.

Changing an entity: edit the class, then run `npx rayfin up` (or `npx rayfin up db apply` for the schema only). Destructive changes need `--force` and a review.
